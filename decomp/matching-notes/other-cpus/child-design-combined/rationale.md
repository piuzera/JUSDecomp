# Combined native program owner

## Problem

The child is one NitroFS program containing compressed ARM9 and independent ARM7. Existing ARM7 operations own two physical images, while child encoding deliberately delegates native provenance to its caller. Giving the packer two CPU authorities exposes their shared child identity and whole-program preservation rules. A combined owner can prove those rules once without rewriting the approved ARM7 producer.

## Usage (caller's view)

[Usage first](usage.md) defines three call sites. The verifier builds one combined operation from the existing ARM7 operation and child approvals. The packer consumes its three disjoint auxiliary writes. Audit consumers receive detached reports. [The signatures](shape.py.txt) follow those calls.

## Shape

Add `tools/scripts/native_program_baseline.py`, a Python owner for the child program and the auxiliary write set. It contains the fresh child reference build internally and retains the existing ARM7 live operation. Its public operation hides exact executable discovery, strict analyzer initialization, link provenance, relocation interpretation, encoding, and identity reconciliation, per boundary-discipline. CPU-specific scripts are implementation dependencies, not competing packer authorities.

The immutable capture binds current build identity, original parent and child bytes, every consumed helper/source/approval/tool, actual command evidence, and expected artifact digests. Rechecks validate that capture before reading artifacts, then validate containment, every symlink component, timestamps, required-file inventory, all input/tool hashes, commands and outputs. Expected hashes come from the successful initial proof and never from mutable files at recheck time. Reports return copies. No public constructor or detached JSON can confer fresh-build authority, per encode-lessons-in-structure.

`verify.py` retains `arm7_native_baselines` and adds `child_native_programs` before freshness only when child mode is selected. The combined operation's outer status is `passed`; nested codec status stays `binary_roundtrip_verified`. Fold its complete input and artifact inventories into canonical freshness. Keep default 19 and paired ARM7 20 stages unchanged. Source0, global executable completeness unknown, and T10 open remain explicit.

`rom_roundtrip.py` accepts the combined operation as an alternative to the legacy ARM7 operation. It retains one occupied list for all 17 parent ARM9 writes and the three auxiliary writes. Validate the whole set before application. The child ARM9 write precedes the two ARM7 writes. After both child writes, compare the entire child program against its pinned original hash. Never write the whole codec-produced child into the parent. Recheck the operation before publication and retain existing final ROM freshness checks.

## Fresh child proof

Derive `ChildRom/JSS2Child.srl`, file ID79, from the actual original parent and current FNT/FAT mapping. Require parent child extent `[0x23b800,0x4464c8)` and its pinned whole-program digest. Use the full program identity and CPU to select the ARM9 row generated by `verify_other_executables`; a saved first ARM9 row is insufficient.

Run fresh extraction and strict `init`, then `delink`, `lcf`, and native link. Permit only the exact known generated `delinks_path` correction, retain before/after config digests, and reject missing fields. Bind tool versions, actual argv/cwd, logs, symbols, sections, relocation metadata and delink layout. Require the original three gap objects and their independent raw digest pins. Reuse `verify_link_record` and additionally bind `link.map` to actual `-Map` argv in this reference-only path. Strict calls remain enabled.

Check DSD modules and symbols through diagnostic `dsd-check.elf`, while canonical `linked.elf` owns payload and relocation proof. Validate all three modules' sections, initialized prefixes, emitted metadata and original BSS boundaries. `verify_extracted_arm9_modules` permits only the known four-byte compression-pointer normalization. Validate all 35,092 original relocation slots against canonical ELF using fresh unnormalized gap objects. Require totals ARM9 34,992, ITCM78, DTCM22, types1 10,755, type2 20,440, type10 3,897, no failure/unresolved/source fallback. Diagnostic ELF and normalized objects cannot replace original relocation authority.

Use existing `repack_child_arm9` unchanged. Prove exact encoding and whole-child equality, then capture output size/digest and read its checked compressed slice. The combined owner validates child ARM7 through its subordinate ARM7 operation using that child's identity even if its image equals parent ARM7. Preserve child header, nine-byte FNT, empty FAT, assets, signature, padding and 396-byte inter-CPU gap. ARM9 writes parent `[0x23f800,0x41d074)` and ARM7 writes `[0x41d200,0x4458b0)`. Header entry0x02000850 remains independently checked from linked ELF entry0x02000000; this is payload/layout proof, not bootability.

Production DSD pin prefix222587 remains unchanged. Child analysis uses separately approved analyzer CLI prefix3f18 and its complete source context. Codec approval is separate and cannot follow implicitly from analyzer approval. The codec uses unchanged ds-rom0.8.0 source and recorded build context from the integration contract. All 16 existing ARM7 approval artifacts remain untouched; the new owner and child approvals must be separately inventoried without extending that pinned manifest in place.

## Module map

| Module | Ownership |
| --- | --- |
| `verify.py` | Mode validation, mandatory stages, canonical freshness and source accounting |
| `native_program_baseline.py` | Fresh child build, combined immutable evidence, complete auxiliary writes and child identity |
| `arm7_native_baseline.py` | Existing approved paired ARM7 operation, unchanged |
| `child_rom_roundtrip.py` | Existing exact codec assembly/encoding, unchanged |
| `rom_roundtrip.py` | One extent inventory, application, whole child/parent checks and publication |

The reader traces verifier, combined owner and packer in three files. Existing proof helpers supply domain algorithms without exposing extra caller stages, per minimize-reader-load.

## Synthesis decision

Candidate recommendation only; the parent architect chooses the final base. Prefer the Python combined owner over extending ARM7's approved implementation or moving the whole program into a new Rust stage. It centralizes the shared child identity and proof while preserving reviewed producer provenance.

## Tradeoffs accepted

- We accept Python coordination across existing proof helpers in exchange for retaining current analyzer/linker checks and approvals.
- We accept paired ARM7 as a prerequisite in exchange for one complete child proof and no partial combined success.
- We accept one additional live owner retaining a subordinate operation in exchange for one auxiliary authority at packing.

## Alternatives considered

Extend `arm7_native_baseline.py` into a combined CPU owner. This hides coordination from callers, but changes an approved source artifact and forces approval renewal of the existing producer context. Its ARM7 physical receipt schema also cannot carry strict ARM9 relocation and codec evidence without becoming a different contract.

Create a native Rust whole-program stage. This could deeply hide both CPU pipelines behind one producer, but must port or safely consume Python strict linker, ELF, relocation and codec checks. Its CLI receipt cannot itself supply in-process authority. New binary/source approvals and duplicated proof rules are a larger integration cost than the Python owner's retained live subordinate operation.

Add a public per-CPU child helper. It is bounded and preserves ARM7, but exposes shared child provenance and requires packer coordination between authorities. The combined owner hides those checks behind one recheck result.

## Open questions and risks

Does the owner approve the analyzer prefix3f18 and separate codec source/binary context needed for a fresh canonical child run? Can implementation preserve private construction and immutable captures under the current dynamic `load_script` pattern? Neither question changes source credit or T10 status.

The integration contract supplies strict child totals, pins and extents. Existing code explicitly forbids JSON-only ARM7 packing and delegates child link authority; that evidence motivates retaining live operations. The broader historical motivation was not independently researched in this bounded design candidate.

Red-flag review: no caller-controlled internal build stages, no public receipt schema, no stage-by-stage forwarding modules, and no public CPU selection or arbitrary output write list. The combined owner adds identity reconciliation and full proof capture rather than merely forwarding ARM7 calls. This package runs no ROM build and changes no implementation, approvals or production pins.
